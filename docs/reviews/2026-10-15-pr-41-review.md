## Findings

### 🔴 F1 (P1) — `gcp-backend.md`: `metrics-db-url` secret referenced but never created or granted  *(triple-confirmed: security M2, architecture H1, accuracy P2)*
§4 deploys `--set-secrets="LIVEKIT_API_SECRET=livekit-api-secret:1,METRICS_DB_URL=metrics-db-url:1"`,
but §3 only `gcloud secrets create`s `livekit-api-secret`/`azure-openai-key`/`azure-speech-key`
and the `secretAccessor` grant loop iterates only those three. `metrics-db-url` is created/granted
nowhere. An operator running §3→§4 verbatim hits `Secret [metrics-db-url] not found` / permission
denied — and this is the `/admin/*` DB credential path.
**Fix:** add `gcloud secrets create metrics-db-url --data-file=-` in §3 and include it in the grant loop (bound to `token-server-sa`).
**✅ Resolved:** `gcp-backend.md` §3 now creates `metrics-db-url` (DB-password DSN) and includes it in the `token-server-sa` grant loop.

### 🟡 F2 (P2) — `gcp-backend.md`: Secret Manager wiring incoherent + worker creds unencrypted  *(security M1, architecture M1, accuracy P3)*
§3 creates `azure-openai-key`/`azure-speech-key` and grants them to **`token-server-sa`** — but
the token server never uses Azure; only the **worker** does. The worker (§6) loads creds from a
plaintext `--env-file /etc/koperasi/worker.env` on the VM, so (a) the Azure Secret Manager secrets
are consumed by nothing, (b) the LiveKit secret + Azure keys sit **cleartext on disk** with no
ownership/`chmod 600` guidance, and (c) `worker-sa` (referenced at `gcp-backend.md` §6) is never
`iam service-accounts create`d nor granted. Contradicts `production-config.md` §5 ("secrets in
Secret Manager").
**Fix:** either source worker creds from Secret Manager via `worker-sa` (create it + grant the azure/livekit secrets there), or drop the Azure `secrets create`/grant from §3 and document the env-file explicitly with `install -o root -m 600 /etc/koperasi/worker.env`.
**✅ Resolved (Secret-Manager-via-worker-sa option):** §3 now creates `worker-sa` and splits grants by consumer (token-server-sa → livekit + metrics-db-url; worker-sa → livekit + azure-*). §6 fetches secrets from Secret Manager at boot via `worker-sa` into a tmpfs `/run/koperasi-worker.env` (`0600`, removed on stop); only non-secret vars live in `/etc/koperasi/worker.env.base`. Secrets no longer persist plaintext on the VM disk.

### 🟡 F3 (P2) — `README.md` Go/No-Go: worker agent-name parity command returns nothing  *(accuracy P2)*
`gcloud compute ssh voice-worker ... 'systemctl show koperasi-worker -p Environment | grep -i LIVEKIT_AGENT_NAME'`
reads systemd's `Environment=` property, but the §6 unit passes env via `docker run --env-file`
(no `Environment=` directives) — so the grep always finds nothing and the parity gate can't pass.
**Fix:** grep the env-file (`grep LIVEKIT_AGENT_NAME /etc/koperasi/worker.env`) or
`docker exec koperasi-worker printenv LIVEKIT_AGENT_NAME` (matching the correct compose-side check in `backend-containers.md`).
**✅ Resolved:** README Go/No-Go now uses `gcloud compute ssh … 'docker exec koperasi-worker printenv LIVEKIT_AGENT_NAME'`.

### 🟡 F4 (P2) — `backend-containers.md`: "image free of secrets" acceptance command is broken  *(architecture M2)*
`docker run --rm koperasi-api sh -c 'ls -a /app | grep -i env || echo none'` → the image's in-image
virtualenv is `/app/.venv`, and `grep -i env` matches `.venv`, so it prints `.venv` and **never**
`none` — the check can't distinguish the venv from a leaked `.env`. (The live verification earlier
in the session used a correctly-anchored grep, so the ✅ stamp is sound; the *doc command* is wrong.)
**Fix:** anchor it — `ls -a /app | grep -iE '^\.env' || echo none`.
**✅ Resolved:** `backend-containers.md` acceptance now anchors `grep -iE "^\.env"` with a note on the `.venv` false-match.

### 🟡 F5 (P2) — `gcp-backend.md`: `--startup-probe` gcloud flag form unverified  *(accuracy P2, architecture L4)*
`--startup-probe=httpGet.path=/health,httpGet.port=8000` — Cloud Run startup probes were historically
YAML-only; this inline flag/syntax should be confirmed against the current `gcloud` reference before
an operator relies on it.
**Fix:** verify against installed `gcloud`; if unsupported, configure the probe via service YAML and note it.
**✅ Resolved:** added a ⚠️ caveat in §4 telling the operator to verify the flag against their `gcloud` version and fall back to `gcloud run services replace service.yaml` if the inline flag is unavailable (gcloud wasn't installed to verify here).

### 🟡 F6 (P2) — `production-config.md` §1: "one set, two encodings" mis-frames CORS vs CSP  *(architecture M3)*
The summary says CORS and CSP `connect-src` encode "the **same** set." They don't: `CORS_ALLOW_ORIGINS`
lists the **callers** `{app, admin}`; CSP `connect-src` lists the **callees** `{api, supabase, wss:}`.
The individual bullets are correct, but the "same set" line invites putting `api` into CORS or
`app/admin` into `connect-src`.
**Fix:** reword to "the production domain *triplet* partitioned across two mechanisms (callers→CORS, callees→CSP)."
**✅ Resolved:** §1 retitled "triplet domain, dua mekanisme"; CORS now explicitly = callers (`app`,`admin`, not `api`), CSP `connect-src` = callees (`api`+Supabase+`wss:`, not `app`/`admin`), with a "don't cross them" warning.

### 🔵 F7 (P3) — `backend-containers.md`: mis-quoted 500 response body  *(accuracy P3)*
Quotes the unconfigured-JWT 500 as "Konfigurasi verifikasi JWT belum lengkap" — that's the
`log.error` string (`auth.py:140`); the actual HTTP body detail is **"Auth belum dikonfigurasi"**
(`auth.py:141`).
**Fix:** quote the response-body string an operator would see.
**✅ Resolved:** now quotes body `detail:"Auth belum dikonfigurasi"` (auth.py:141) and labels the other string as the server log.

### 🔵 F8 (P3) — `frontend-vps.md`: HSTS snippet contradicts its own advice + imprecise scope  *(security L1)*
The snippet ships `max-age=31536000; includeSubDomains` (a committed 1-year policy) while the warning
says "start with a small `max-age` at bring-up." Also, `includeSubDomains` on `app.<domain>` covers
`*.app.<domain>`, not the sibling hosts `admin.`/`api.` (header is per-host) — the "covers app/admin/api"
note misstates the mechanism (errs safe, but imprecise).
**Fix:** ship a small `max-age` initial value (or state the snippet is the post-ramp target), and correct the scope wording.
**✅ Resolved:** snippet now ships `max-age=300` (bring-up) with a note to raise to 1y after TLS is stable; dropped `includeSubDomains` from the default and corrected the per-host scope wording (`app.<domain>` covers `*.app.<domain>`, not sibling hosts).

### 🔵 F9 (P3) — worker "hard session timeout" cited as #1 cost lever but never operationalized  *(architecture L1)*

**Fix:** name the concrete knob (worker-side session timeout in `voice_agent.py`/`AgentSession`) or mark it an explicit follow-up.
**✅ Resolved:** verified no session cap exists in `voice_agent.py`; docs no longer imply one.
